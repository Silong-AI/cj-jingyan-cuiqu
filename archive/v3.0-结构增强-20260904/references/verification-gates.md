# 验证门禁与落地验证（Verification Gates）—— CJ·经验萃取 v2.0

把"验证"从一句"小范围试用"升级为**三道硬门禁 + 一套落地验证协议**。萃取出的每一条干法，都必须能回答"凭什么说它有效"。

## 一、三重验证门禁（每一条干法必过）

每个候选干法（方法/牛招/心法）在封装前，必须过三道验证。**任何一条不过，降级或淘汰**：

| 验证 | 判断问题 | 通过标准 |
| --- | --- | --- |
| **V1 跨域复现** | 这个做法在 ≥2 个不同场景/案例/对象上验证过？ | 有复现证据，不是一次偶然 |
| **V2 预测力** | 能凭它回答一个"没说透"的新问题/新场景？ | 有生成力，不只是记录 |
| **V3 独特性** | 不是任何聪明人都知道的常识？ | 有差异，值得封装 |

- 三重全过 → 标记为**可封装干法**，进入封装。
- 仅 1-2 重过 → 降级为"参考做法"，注明证据薄弱。
- 0 重过 → 淘汰，写入 `rejected/` 留审计（不删除记录）。

> **审计轨迹**：保留 `verified/` 与 `rejected/` 两份清单，每条注明通过/淘汰理由，方便回溯。

## 二、成果校验清单（封装前逐项过）

任何成果物（SOP/课程/案例库/技能包）在交付前，必须过下面的清单，**缺一项就补齐**：

### SOP / 标准动作类
- [ ] 有明确的适用场景与边界
- [ ] 步骤可数、顺序明确（第一步到第 N 步）
- [ ] 每步含：**动作 + 要点 + 常见错误/反例**
- [ ] 有可量化验证指标（怎么知道有效）
- [ ] 有"新人照做能到什么程度"的预期

### 案例库类（STAR）
- [ ] 有数据（量化结果）
- [ ] 有对标（和谁比、好多少）
- [ ] 有金句（一句可传播的总结）
- [ ] 有画面（细节可"看见"）

### 培训课程类
- [ ] 有学习目标（业务目标 + 行为指标）
- [ ] 有训战闭环（训练→演练→实战→带教→复盘）
- [ ] 有演练剧本（场景/角色/话术/反馈）
- [ ] 有考核方式（怎么算学会了）

## 三、经验落地验证协议（组织场景最缺的一环）

萃取出的干法，要**用数据证明有效**，不是"感觉有用"：

### 1. 试点对照（A/B 验证）
- 选两组同质团队/个人：**试验组用新干法，对照组用旧做法**。
- 设定同一指标（转化率/客单价/留存率/耗时），跑 2-4 周。
- 对比差异，写进验证报告：`验证结论 + 数据 + 边界条件`。

### 2. SOP 可用性测试（直接对应"80% 目标"）
- 让一个**没听过这套方法的新人**，只靠 SOP 独立执行一遍。
- 观测：能否做到 60 分？（能→SOP 可复制；不能→回炉补细节）
- 记录他卡在哪一步——那里就是要补的"动作/工具"层。

### 3. 冲突仲裁（多位高手做法矛盾时）
多位高手的做法冲突时，不掩盖，走仲裁：
| 步骤 | 做法 |
| --- | --- |
| 1 并列呈现 | 把矛盾做法并列展示，标出各自的适用场景 |
| 2 找共同底层 | 问"两种做法的共同底层原则是什么"（往往不矛盾） |
| 3 场景切分 | 按场景/客户/阶段切分，各自适用 |
| 4 留默认+特例 | 定一个默认做法，冲突做法作为"特定条件下的特例" |
| 5 试点裁决 | 用试点对照数据最终裁决 |

### 4. 经验过期检测（防止经验失效）
- 每次封装标注**信息截止时间**与"哪些环节最可能随市场变化失效"。
- 建议定期（如每季度）对高价值干法做一次"仍有效吗"复核：
  - 底层原则是否仍成立？→ 保留
  - 具体动作是否已被工具/市场淘汰？→ 更新动作、保留原则

## 四、萃取四原则的落地版

> **有经验必萃取 → 有萃取必验证 → 验证后必固化 → 固化后必迭代**

- **必萃取**：只在有使用场景时萃（给谁用、解决什么问题）。
- **必验证**：走三重验证门禁 + 试点对照。
- **必固化**：通过验证的干法才进入 SOP/技能包/培训体系。
- **必迭代**：固化后定期复核，防止过期。
